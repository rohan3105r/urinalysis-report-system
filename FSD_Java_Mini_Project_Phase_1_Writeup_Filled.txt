1. Project title, selected institute case study/use-case ID, one-sentence MVP statement, users and 3–5 core features.
Project title: Urinalysis Report Management and Decision-Support System
Selected institute case study / use-case: Urinalysis sample reporting and AI-assisted abnormality review support for laboratory workflows.
Use-case ID: URI-AI-01 (Institute AI case study: Urinalysis decision support)

MVP statement: The system allows laboratory staff to record urinalysis test results, view stored reports, and flag abnormal findings using a rule-based decision-support workflow so that clinically relevant variations can be reviewed quickly.

Users:
- Lab technician / sample entry operator
- Clinician / doctor reviewing the report
- Administrator or supervisor monitoring workflow status

Core features:
1. Enter and save urinalysis test details for a sample record.
2. View the history of stored test reports in a searchable dashboard.
3. Flag abnormal findings using a demonstration rule engine for pH, specific gravity, blood, protein, ketones, nitrite and leukocytes.
4. Display patient-facing and clinician-facing summaries for each sample.
5. Monitor dashboard counts for total tests, flagged tests and clear tests.

Planned AI / Intelligent Component
- Rule-based abnormality detection and review prioritization
- Future extension: predictive classification or recommendation engine for abnormal urine patterns

3. Main entities/resources
Primary resource: UrinalysisTest
Important fields:
- id: unique record identifier
- sampleId: sample reference number
- testDate: date of test
- ph: urine pH value
- specificGravity: specific gravity reading
- urineColor: observed urine appearance
- glucose, protein, ketones, blood, nitrite, leukocytes: qualitative or semi-quantitative findings
- flags: list of abnormal conditions detected by the rule engine
- normalFindings: clinically reassuring findings
- abnormalFindings: concerning findings
- reviewStatus: No flags / Review recommended
- priorityLevel: Low / Moderate / High
- patientMessage: patient-friendly explanation
- doctorSummary: clinician summary
- notes: free-text observations
- createdAt, updatedAt: record timestamps

Secondary resources / concepts:
- Patient record metadata (sample identification and test date)
- Report summary object for dashboard statistics and flagged records

4. REST endpoints for one primary resource
Resource: UrinalysisTest

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | /api/tests | Fetch all urinalysis records |
| GET | /api/tests/{id} | Fetch a single test record by ID |
| POST | /api/tests | Create a new test record |
| PUT | /api/tests/{id} | Update an existing record |
| DELETE | /api/tests/{id} | Delete a record |
| GET | /api/tests/stats | Get summary metrics such as total, flagged and clear tests |

5. Repository organization and implementation
The project was organized into two main modules:
- backend/ – Spring Boot application with model, repository, controller and configurations
- frontend/ – React + Vite user interface for data entry and reporting

The backend exposes REST APIs and the frontend calls them using fetch requests to save and retrieve records.
The application demonstrates one complete end-to-end workflow: form submission -> API call -> MongoDB persistence -> UI display and report summary.

- User value: helps laboratory and clinical staff quickly identify samples requiring attention and review before manual interpretation

Postlab questions:

1. What is the MVP of your selected case study, and which user problem does it solve?
The MVP is a lightweight urinalysis reporting system that allows lab staff to capture sample test data, review abnormal findings, and generate a summary for further clinical attention. It solves the problem of manually tracking urine-test results and quickly identifying records that need review.

2. Why did your team choose the implemented feature as the first end-to-end vertical slice?
This feature is the most visible and essential workflow in the application: capturing a test result, persisting it in the database, and displaying it in the UI. It provides a complete backend-to-frontend data flow and demonstrates the core architecture of the project.

3. Explain how data travels from the React interface to Spring Boot and the database in your implementation.
The React frontend captures user input in a form, serializes it to JSON, and sends it to the Spring Boot REST API using fetch. The API controller validates the request and calls the repository to persist the record in MongoDB. When a user later fetches reports, the backend reads from MongoDB and returns the data to the React interface for display.

4. Which entities/resources are central to the project, and why?
The central resource is UrinalysisTest because it stores all the test values, computed flags, status, notes and summary messages. It contains the main operational data that drives both the dashboard and the decision-support function.

5. What AI/intelligent functionality is planned, what inputs will it use, and what output will it produce?
The planned intelligent feature is a decision-support layer that evaluates urinary findings and flags abnormal patterns. It will use inputs such as pH, specific gravity, blood, protein, nitrite, leukocytes and color. It will produce a review status, priority level, summary notes and recommendation support for further evaluation.

6. Which parts of the final project remain to be implemented after Phase 1?
The remaining work includes deeper AI or ML classification, user authentication and role-based access, stronger data validation, export/report generation, and full deployment configuration. Phase 1 establishes the MVP foundation and core data flow, while later phases can extend the system with more robust clinical decision support.
